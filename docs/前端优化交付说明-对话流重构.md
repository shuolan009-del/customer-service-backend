## 四、时间轴方案（本轮最需要知情的取舍）

### 为什么需要

```
GET /api/chat/history → HistoryMessage = { session_id, role, text, object }   ← 零时间字段
```

后端内部的时间戳只到 **Session 级**（`domain/state.py:24-26` 的 `started_at` /
`last_activity_at` / `closed_at`），`load_chat_history` 不往外传；`Turn` /
`UserMessage` / `BotMessage` **全部无时间字段**；`session_id` 是 `str(uuid4())`，
反推不出日期。**在后端零改动的前提下，前端只能自己记时间。**

### 做法（路线 A：前端 localStorage 时间轴）

- 本浏览器**发出/收到**的消息 → 打 `Date.now()`，落 `localStorage` 键 `cs-ts:v1:<sender_id>`
- 历史接口返回、本机没记录过的旧消息 → 无时间 → 归入「更早的记录」
- **指纹**（关键）：`HistoryMessage` 没有 `message_id`，无法与本地记录一一对应，于是用
  `角色 + 类型 + 对象 id + 文本 + 同内容第几次出现` 生成稳定键。
  后端按 session/turn 顺序稳定展开历史，所以**刷新后同一条消息能重新命中**。
- 保留 30 天 / 最多 1000 条，自动裁剪。

### 已知取舍（必须知情）

| 取舍 | 影响 |
|---|---|
| 跨浏览器 / 清缓存后旧消息无时间 | 退化为「更早的记录」，不丢消息、只是没有日期标签 |
| 同一发送者**跨天**说过「完全相同的第 N 次同样的话」 | 会命中较新那条的时间，即被归到较新那天（分组只用「天」，影响很小） |
| 时间粒度是**本地记录时刻**，不是服务端时刻 | 本机时钟偏差会直接反映到标签上 |

### 如果以后允许动后端

只需 2 文件约 3 行即可让日期分组完全真实（`HistoryMessage` 加 `started_at` +
`load_chat_history` 透传 `session.started_at`），可与本方案叠加：有真时间用真时间，
没有回落本地时间轴。**本轮未做，因为你要求后端零改动。**
