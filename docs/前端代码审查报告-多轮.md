## 二、P1 详情

### P1-1　WS 断线时，用户消息静默丢失

- **位置**：`composables/useAvatar.js:172-178` + `composables/useChat.js:248-255`
- **根因**：`avatarWs.send()` 返回 `false`（socket 已不在 OPEN 态）时，代码走 `if (!sent) finish()`，而 `finish()` 无条件 `resolve(true)`。useChat 的 WS 分支拿到 `true` 就 `return`，**不回退 HTTP、不报错**。
- **触发路径**：`canUseWs()` 检查与 `send()` 之间 WS 断开（网络抖动 / 后端重启重连窗口）——真实会发生，不是理论边界。
- **用户视角**：输入框清了、消息气泡在列表里、没有任何回复、没有任何错误提示。
- **最小修复**（两处，共约 4 行）：
  ```js
  // useAvatar.js：finish 带上发送结果
  const finish = (sent = true) => { ... resolve(sent) }
  ...
  const sent = avatarWs.send({...})
  finish(sent)            // 原来是 if (!sent) finish() → resolve(true)
  ```
  ```js
  // useChat.js：WS 分支拿到 false 时回退 HTTP，而不是直接 return
  const sent = await avatar.sendViaWs(payload.text)
  if (sent) return        // 真正发成功了才结束
  // 落到下面的 HTTP 分支重发（user 消息已在列表里，不会重复 append）
  ```

### P1-2　右侧业务对象列表无 sender_id 守卫（竞态）

- **位置**：`composables/useSidebar.js:15-48`（对比 `composables/useChat.js:219` 的守卫）
- **根因**：`fetchHistory` 有 `if (sid === senderId.value.trim())` 防串台，`useSidebar.load` 没有。快速连续修改 sender_id 输入框时，先发的请求后返回，把**旧 sender 的订单/商品**写进当前列表。
- **最小修复**（约 3 行）：
  ```js
  async function load(senderId) {
    const sid = String(senderId ?? '').trim()
    ...
    const [ordersResponse, productsResponse] = await Promise.all([...])
    if (sid !== String(senderId ?? '').trim()) return   // 已切换身份，丢弃过期响应
  ```
  更稳的做法是加请求序号（`let loadSeq = 0; const seq = ++loadSeq; ... if (seq !== loadSeq) return`），可同时解决 P2-5 的 loading 闪烁。

## 四、P3 / 已知取舍（不建议改，列此备查）

1. **日期分组的时间来源是前端 localStorage 指纹**（`utils/timeline.js`）。后端零时间字段是硬约束（已对账 `api/schemas.py`）。代价：跨浏览器/清缓存后退化为「更早的记录」；跨天说完全相同的话会命中较新时间。要彻底真实需后端加 2 文件约 3 行（`HistoryMessage` 加 `started_at` 并透传），属单独决策。
2. **数字人连接链路未验证**：`XMOV_ENABLED=false` + 无头浏览器无真实 GPU。面板/按钮/进度/状态机代码路径已 review，但取凭证→加载 SDK→连房间→WS 重连需本机真实 Chrome 确认。
3. **fetch 无超时**：全部请求无 `AbortController`，后端挂起时 `isSending` 会卡住。加超时会改变失败时的行为语义，建议与 P1 修复分开评估。
4. **`format.js:9` 用全角 `￥`（U+FFE5）**：中文场景显示正常，非 bug。
5. **`messageGroups` 靠直接赋值 `message.at` 触发重算**：正确利用了 ref 深度响应式，非问题，仅说明为何 stamp 后分组即时更新。
6. **`useChat` 单例 `containerEl` 在离开工作台后悬空**：期间 WS 已断、无 watch 触发，返回时 `setContainer` 刷新，安全。

### 排障备注（测试手法坑，非应用缺陷）

CDP `Input.dispatchKeyEvent` 的 `keyDown` **必须带 `text: '\r'`**，Chrome 才会合成 keypress，form 隐式提交（Enter 发送）才会触发。不带 text 时 keydown 监听器能收到事件、默认动作却不执行——首轮 Enter 测试超时即此因，已变体实验（keyDown+text / rawKeyDown+char / char-only）确认仅前者稳定触发且恰好一次。该经验已回写至 headless-cdp-verify 技能。
